# GuardBench 코드 리뷰 스킬

팀의 `guardbench-backend/docs/ai-development/review.md` (APPROVED) 규칙을 실행하는 루프다.

## 원칙

리뷰만 요청받았다면 **파일 수정, commit, push, 승인, 병합을 하지 않는다.** 목적은 중요한 결함을 빠르게 찾고 사람이 승인 판단을 하도록 돕는 것이다.

## 검토 순서

1. Issue/PR의 base·head, 변경 파일, 완료 조건을 확인한다.
2. 변경과 직접 관련된 `APPROVED` 계약, 테스트, 공개 코드를 확인한다. `DRAFT`는 확정 근거로 쓰지 않는다.
3. 실제 diff를 기준으로 다음을 먼저 찾는다: 계약 회귀, 데이터 손실, 보안, 동시성·트랜잭션, 주요 기능 오류.
4. 리뷰 단위 커밋(Domain/Port, Adapter, Test, Docs)이 논리적으로 분리됐는지 확인한다.
5. 테스트가 결함을 잡는지 확인하고, 실행 못 한 검증은 미검증 위험으로 기록한다.
6. 스타일·선호는 정확성 문제와 분리한다.

PR 설명·주석만 믿지 않는다. 결함 단정에는 재현 동작·코드 경로·테스트·계약 근거가 필요하다. 가능성만 있으면 `질문` 또는 `미검증 위험`으로 표시한다.

## 심각도 / 차단 여부

| 등급 | 기준 | 기본 처리 |
| --- | --- | --- |
| P0 | 보안 사고, 데이터 손실, 서비스 전체 장애 | Blocking |
| P1 | 공개 계약 회귀, 주요 기능 오류, 잘못된 권한·트랜잭션·동시성 | Blocking |
| P2 | 제한된 조건의 실제 오류 또는 완료 조건 누락 | 영향에 따라 명시 |
| P3 | 사소한 품질·가독성 개선 | Non-blocking |

## 발견 사항 형식

```
[P1][Blocking] 짧은 제목 — path/to/File.java:42
어떤 입력·상태에서 무엇이 잘못되는지 (최대 3문장).
근거 계약/테스트 연결 + 최소 수정 방향.
```

## 결과 형식 (권고 상태부터, 12줄 안팎)

- `Approve`: Blocking 없음
- `Comment`: 질문·Non-blocking 제안만
- `Changes requested`: Blocking 1건 이상

## 문맥 경계

현재 PR/Issue 범위에 집중한다. 무관한 이슈·worktree·커밋을 언급하지 않는다 (PR #77 회귀 방지). 연관성이 필요하면 관계·선후관계를 먼저 명시한다.

## 완료 확인

- Blocking마다 위치·영향·근거가 있는가
- 검증된 결함과 미검증 위험을 구분했는가
- Issue 범위 밖 개선을 승인 조건으로 만들지 않았는가
- 발견이 없어도 미검증 영역을 숨기지 않았는가
