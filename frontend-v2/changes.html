v2 Candidate · 사용성 개선안

현재 화면을 더 쉽게 만들었습니다

현재 공식 프론트엔드는 도메인 전문가에게는 정확하지만, 처음 보는 사용자에게는 전문 용어(Baseline, Candidate, Assertion, Quality Gate, Snapshot...)가 많아 이해가 어렵습니다. v2 후보는 API 계약과 도메인 규칙의 의미는 그대로 유지하면서, 화면의 표현·명칭·설명만 사용자 친화적으로 개선한 제안입니다. 지금은 실행 이력 → 결과 상세 → 테스트별 비교까지 실제로 클릭하며 이동하는 3단계 작동 목업으로 동작합니다.

지켜진 것: 3축 상태 분리 원칙, 평가 계약(보안 회귀 0건 등 Quality Gate 기준), API 엔드포인트·요청/응답 구조, enum 값의 실제 의미. 화면 표현만 바꿨고 데이터 계약은 건드리지 않았습니다.

3단계 depth로 작동합니다

Depth 1 · 실행 이력

검증 실행 목록. 진행 상태·실행 결과·배포 판정을 한눈에. 행 클릭 → 상세로.

Depth 2 · 결과 상세

3축 상태 설명 + 배포 판정 + 지표 4종 + 테스트별 판정 테이블. 행 클릭 → 비교로.

Depth 3 · 테스트별 비교

입력 프롬프트 + 현재/변경 예정 정책 응답 Diff + "이 결과의 의미" 해설.

실행 #5001(배포 차단), #5000(배포 가능), #4999(검증 중), #4998(부분 완료), #4997(판정 불가) — 5가지 상태 조합을 모두 클릭해 확인할 수 있습니다.

1

전문 용어에 쉬운 이름과 툴팁을 붙였습니다

핵심 도메인 용어는 화면에서 쉬운 표현으로 바꾸되, 원래 용어를 괄호와 툴팁으로 함께 보여줘 정확성을 잃지 않게 했습니다.

기존 표현 v2 표현 변경 이유
Baseline현재 운영 정책 (Baseline)"무엇을 비교하는지" 직관적으로 전달
Candidate변경 예정 정책 (Candidate)검증 대상임을 명확히
Expected정답"사람이 정한 기대 동작"을 쉽게
Assertion (PASS/FAIL)정답 일치 (일치/불일치)Gate 판정과 헷갈리지 않게
Change이전 대비 변화비교의 의미를 서술형으로
Security/Usability Regression보안 회귀 / 과잉 차단한글 지표명 + 한 줄 설명 툴팁
Quality Gate PASS/FAIL배포 가능 / 배포 차단최종 결론을 행동 중심으로
Snapshot테스트 (건)일반 사용자에게 익숙한 단위로
2

혼동되던 3가지 상태를 눈에 보이게 분리했습니다

기존 화면은 진행 상태 · 실행 결과 · 배포 판정을 각각 배지로만 표시해, 사용자가 "실행 오류"와 "배포 차단"과 "판정 불가"를 헷갈리기 쉬웠습니다. v2는 결과 상세 상단에 3단계 설명 카드를 추가해 각 상태가 무엇을 뜻하고 어떤 순서로 흐르는지 한눈에 보여줍니다.

1. 진행 상태 — 검증 작업이 어디까지 왔나 (대기 → 준비 → 검증 → 종료)

2. 실행 결과 — 테스트가 오류 없이 다 돌았나 (정상/부분/오류)

3. 배포 판정 — 이 정책을 배포해도 안전한가 (가능/차단/판정불가)

이 분리는 팀의 APPROVED 계약(HTTP 오류 ≠ Execution ERROR ≠ Assertion FAIL ≠ Quality Gate FAIL)을 그대로 반영한 것으로, 규칙을 바꾼 게 아니라 규칙을 더 잘 보이게 만든 것입니다.
3

오라벨 버그를 바로잡았습니다

기존 코드에서 상세 비교 모달의 StatusPill이 kind="assertion" 없이 호출되어, 테스트의 정답 일치(PASS)가 화면에 "Gate 통과"로 잘못 표시되는 문제가 있었습니다. (근거: src/components/common/StatusPill.tsx의 generic 분기가 raw PASS를 gate로 해석)

기존 (잘못됨)

테스트 정답 일치 → "Gate 통과" 로 표시

v2 (수정)

테스트 정답 일치 → "일치" 로 표시 (배포 판정과 완전 분리)

4

개발자용 문구를 사용자 문구로 바꿨습니다

화면에 노출되던 API 경로와 기술 용어를 사용자 언어로 교체했습니다. (동작은 동일, 표시만 변경)

기존 (개발자 문구) v2 (사용자 문구)
POST /api/v1/test-suites →"이름, 설명, 초기 테스트를 한 번에 등록"
(DELETE /test-cases)"테스트 케이스가 삭제되었습니다"
materialize / numbered Version"초안을 고정된 버전으로 발행"
"리포트" (영문 혼용)"보고서 저장"
5

지표마다 "왜 중요한지" 설명을 추가했습니다

4개 지표 카드(기대 동작 충족률, 보안 회귀, 과잉 차단, 실행 성공률)에 합격 기준과 의미를 툴팁·부제로 붙였습니다. 특히 보안 회귀 카드는 "허용치 0건" 배지와 붉은 강조로 가장 중요한 지표임을 시각적으로 부각했습니다.

판정 테이블 하단에는 용어 범례를 상시 표시해, 표를 보다가 바로 의미를 확인할 수 있게 했습니다.

실제 코드 반영 시 (제안)

이 v2는 개인 레포의 프로토타입입니다. 실제 guardbench-frontend(기관 레포)에 반영한다면 다음 범위로 Issue를 나누길 권합니다:

  • 라벨 레이어: StatusPill.tsx의 label 매핑과 assertion kind 버그 수정 (독립 커밋)
  • 용어/툴팁: 각 View의 문구를 상수로 분리하고 툴팁 컴포넌트 추가
  • 설명 카드: ResultDetail 상단 3축 안내 카드 컴포넌트 추가
  • 정리: 화면 노출 API 문구 제거, SuiteStatus의 'ACTIVE'/'활성' 불일치 정리

※ 기관 레포 변경은 팀의 워크플로(Issue → worktree → 리뷰 → 승인)를 따릅니다. 이 프로토타입은 그 논의의 출발점입니다.
