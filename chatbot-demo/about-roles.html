자주 하는 오해 바로잡기

"챗봇을 GuardBench로 필터링한다"는 오해입니다

챗봇 입력을 실시간으로 걸러내는 건 Guardrail이고, 그 Guardrail 정책을 배포 전에 시험하는 게 GuardBench입니다. 둘은 작동 시점도, 역할도 다릅니다.

🛡️

Guardrail (Amazon Bedrock)

런타임 필터 · 평상시 상시 작동

  • 사용자 입력/출력을 실시간으로 ALLOW/BLOCK 판정
  • 매 요청마다 작동 (챗봇 데모의 "1차 필터"가 이것)
  • ApplyGuardrail API — 모델 호출과 분리된 독립 평가
  • 비유: 문 앞에 상주하는 경비원
🧪

GuardBench (우리 프로젝트)

테스트 도구 · 버전업 시에만 작동

  • Guardrail 정책을 바꿀 때 배포 전 검증
  • 현재 정책(v7) vs 변경 예정 정책(v8)을 같은 테스트로 비교
  • 보안 회귀·과잉 차단을 찾아 배포 판정 (Quality Gate)
  • 비유: 경비원 채용 시험 (실전 투입 전 시험)

Q&A로 정리

Q. GuardBench가 챗봇 입력을 1차 필터링하나요?

아니요. 실시간 필터링은 Guardrail의 역할입니다. GuardBench는 그 Guardrail 정책이 안전한지 배포 전에 시험할 뿐, 런타임 트래픽에는 개입하지 않습니다.

Q. 그럼 이건 시스템 프롬프트/컨텍스트인가요?

아니요. 시스템 프롬프트는 LLM의 답변 방식을 지시하는 문장입니다. Guardrail은 그와 별개 계층에서 입력/출력이 정책을 위반했는지만 판정합니다. ApplyGuardrail은 모델 응답을 요청하지 않고 텍스트만 받아 ALLOW/BLOCK을 돌려줍니다.

Q. 가드레일 정책 변경을 미리 테스트하는 역할이 맞나요?

맞습니다. 팀 계약(ADR 0007, MVP 범위)에 따르면 GuardBench의 정확한 역할입니다.

Q. 평상시엔 작동 안 하고 버전업할 때만 쓰나요?

맞습니다. GuardBench는 CI 게이트처럼 정책을 버전업할 때만 돌립니다. 평상시 실시간 트래픽 처리는 Guardrail이 담당합니다.

한 흐름으로 보면

① 평상시: 사용자 → Guardrail(v7) 필터 → 챗봇 응답

② 정책 개선: v8 초안 작성

③ 배포 전: GuardBench가 v7 vs v8 테스트 → 보안 회귀 발견 → 배포 차단

④ v8 수정 후 재검증 → 배포 가능 → 그때 런타임 Guardrail을 v8로 교체
